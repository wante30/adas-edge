## 2. 三端职责

| 环节 | RK3566 | FPGA | PC 当前阶段 |
|---|---|---|---|
| 视频输入 | 接收 DMA/驱动帧，校验描述符、步长、格式、帧号和时基 | 采集、缓冲、时间戳、必要预处理、PCIe 上行 | 解码官方及新视频，维持真实源帧号和视频时钟 |
| 推理调度 | 前视优先、最新帧优先；RKNN 主模型、灯专项、后续车道分支 | 按已约定格式提供输入，不反复搬运无用全帧 | 同一输入/后处理合同运行冻结 ONNX，提供可重复对照 |
| 场景理解 | 灯色及控制灯归属、左右边界实虚线、导航指令、目标轨迹和危险线索 | 传统图像处理或车道预处理可参与，但需有真实结果合同 | 对每个观察保留来源、置信度、时间和 unknown，检查逐帧错误 |
| 模拟驾驶 | 统一规则引擎：停止、直行、转弯、变道、制动建议、报警 | 接收并显示已确认的方向/报警；回传按键事件 | 原生车机按钮和键盘模拟比赛输入，记录来源，不能伪装识别结果 |
| 输出 | 发送少量结构化结果；本地车机视图消费同一状态 | OSD/LED、HDMI 输出、帧边界应用和状态回读 | 显示真实视频、建议动作、当前模拟状态、来源和待确认项 |
| 运行保障 | 队列丢旧、超时降级、日志、模型版本、复位会话 | 视频不断流、CDC、时序、背压、复位和本地显示保护 | 故障注入、回放重置、协议参考模型和操作流程回归 |

### 2.1 最终屏幕的数据流必须单独确认

当前已讨论的“RK 经 PCIe 回传状态 → FPGA OSD/LED”足以承载箭头、灯色和报警，但不会自动把完整 RK 车机画面送到 FPGA 的 HDMI 输出。

交接时必须根据实际板卡明确最终显示路径：RK 自身的显示输出承载车机主屏，FPGA 的 HDMI 展示采集/预处理/OSD；或者实现一条经过验证的车机图像输入/合成路径，使最终 FPGA HDMI 包含车机画面。后者的带宽、缓存和接口不可由现有 HUD 寄存器替代。正式显示拓扑未确认前，PC 界面完成只算界面与状态消费完成。

## 4. 按交付顺序推进

### P0：四类现场测试有可审计的输入到输出闭环

| 顺序 | 工作包与交付 | PC 验收 | RK/FPGA 放行条件 |
|---|---|---|---|
| P0-1 | 统一车机状态：场景、模拟车道、模拟停/行、系统建议、拒绝原因、报警；图像证据和观察来源可查看 | 同一动作状态驱动大箭头、警告、按钮反馈和日志；暂停不重新推理；换视频和重播清理历史 | 板上按键与 PC 控件映射一致；物理反馈和日志一致 |
| P0-2 | 路口控制灯闭环：圆灯/箭头灯候选、方向关联、unknown、时效 | 标注多段未知路口视频；逐灯组检查漏检、颜色及归属；强制红行必报警，旧绿灯不得继续授予通行 | 冻结对应 RKNN 后在同源帧复测；最终 FPGA 可见输出与源帧同步 |
| P0-3 | 左右边界实虚线：接入独立轻量分支，保留置信度、时间和实例/边界归属 | 至少覆盖左右虚线/实线、双实线、遮挡、弯道、路口缺线；分类不明时不许可变道；强制跨实线报警 | 检查 RKNN 算子/量化、端上耗时；若使用 FPGA 视觉结果，必须验证坐标与边界归属合同 |
| P0-4 | 导航视频输入：先确定素材是屏幕图标/文字、音频还是外部结构化导航；做相应轻量适配 | 导航观察可追溯到源帧；有无效/过期状态；区分预告方向与立即动作；红灯/危险优先于导航 | 同一解析器与状态机上板；端上不能依赖开发电脑或在线服务 |
| P0-5 | 1–2 种危险场景：优先完成行人进入行驶路径、前向碰撞风险等可验证子任务 | 正例、反例、漏检和首次预警时间逐段审查；软件夹具单列；未知不显示“安全” | 实际输入和输出链路测试；如宣称“闯红灯”必须补行人灯归属，宣称“急刹”必须补足运动证据 |
| P0-6 | PCIe 收发与显示故障闭环 | 软件检查重复包、倒序帧、CRC 错、超时、复位、视频切换和保持旧请求；不能用收包时刻刷新旧观察 | 正式驱动/RTL/设备版本锁定；物理断流、暂停像素时钟、设备复位、按键、LED/HDMI 实测 |

P0-1 是当前 UI 工作；完成它不会自动完成 P0-2～P0-6。当前官方视频的人工灯组配置可以保留为可复现演示，但现场未知视频的验收必须另做。

### P1：RK3566 稳定运行与全景、四路能力

1. **锁定部署包。** 收集实际芯片型号、系统镜像、内核、驱动、RKNN runtime 和模型 SHA；模型文件与预处理/解码版本一并冻结。现有 PC FP32 结果只作参考。
2. **单前视整机压测。** FPGA 上行帧 → RKNN → 场景融合 → 决策 → PCIe 下行 → FPGA 可见输出。分开记录采集率、各模型有效更新率、源帧年龄、推理耗时、决策到提交、实际显示延迟，以及 CPU/NPU/内存/温度。
3. **调度与降级。** 当前 PC 名义主模型 10 Hz、灯专项 3 Hz 只是配置。上板先实测，再确定车道与导航频率；前视关键任务优先、队列只保留最新可用帧、显示刷新与推理解耦。超载时降低非关键显示复杂度或副路频率，不累积越来越旧的结果。
4. **全景验证。** 与既有 AVM/LUT 工作单独联调；检查标定来源、投影覆盖、接缝与几何，再接正式 FPGA 工程。已有 LUT/理想存储仿真不替代 DDR、板卡帧率和 HDMI 证据。
5. **四路扩展。** 增加独立 stream_id、帧号与源时间；前视优先并为副路保留调度机会，验证掉一路不阻塞其他流；报告每路有效更新率和带宽，不能用四路文件轮播称为四路并行采集。

### P2：展示质量与提交材料

- 车机采用横向屏幕、清楚的驾驶建议和场景操作。正常画面保留少量关键信息，诊断细节放到可展开区域；红色用于违规/危险，amber 用于待确认，禁止用伪速度/虚构导航填空。
- 真实车道/姿态/轨迹成熟后再增强 3D。保留原项目来源与许可证；不能用堆积车模掩盖投影、尺度、ID 或道路几何错误。
- 录制不超过 3 分钟的 1080P 硬件演示：采集/预处理/PCIe 证据、路口强制违规、虚实线、导航、危险场景、异常回退各有可见结果；源代码、模型清单、版本、时序报告和性能报告可复现。

## 5. PCIe 交接不改动既有语义

1. 上行视频帧合同至少包含 stream_id、source_frame_id、采集时间和时钟域、宽高、format、stride、有效数据长度、缓存所有权/生命周期。具体字段沿用正式驱动，不能在此猜测设备节点或 ioctl。
2. 下行比赛状态需包含观察有效位、灯色、方向关联、左右边界类型、动作、报警、源帧和有效期。图像、检测观察和动作须可关联；不能将不同时间的字段混成刚刚发生的完整观察。
3. 现有 HUD v1 的 `BAR1 0x600–0x63F` 是按交接材料写出的软件合同，尚无本机物理验证。它表示图标状态及事务确认，不具备全部比赛感知语义。
4. ADST v1 是 60 字节软件报文提案，物理地址/邮箱尚未分配；现有 LEFT/RIGHT 表示变道。新内部 `TURN_LEFT/RIGHT` 与 `CHANGE_LEFT/RIGHT` 不能强行塞进旧字段。接线前确定显式转换或新版本，并做 C/Python/RTL 一致性验证。
5. APPLIED、EFFECTIVE 和 HDMI 实际可见是不同层次；去雾覆盖、像素时钟停止、链路复位均需保留专门用例。无法确认的在途事务不能当作成功再发新状态。
6. 时基映射和结果失效由接收侧周期性检查；主机时间、视频时间、FPGA 计数不能直接相减。界面暂停回放和真实输入断流应使用不同会话语义。

### 6.1 完成判定

本轮可以完成 RK3566 工作拆分、PC 车机交互与已有视频功能的全面检查。只有对应真实视频测试、RK3566 实测和 FPGA 物理闭环分别通过，才能逐项把车道、导航、危险识别或整机状态改为已完成；不得由 UI 完成推导算法、板卡或比赛整机完成。
