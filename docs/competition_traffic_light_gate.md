# Traffic light 专项 Gate

更新日期：2026-09-17
范围：仅 FRONT 相机，仅主检测器（COCO `yolo11n.pt`），不启动任何训练
数据：冻结 BDD100K 1000 张 holdout（2734 个红绿灯 GT 框）

## 结论

```
MAIN YOLO NOT SUFFICIENT FOR TRAFFIC LIGHT
```

主检测器**不能**承担红绿灯这一项，原因不是阈值、不是训练量，而是目标在可用特征图上低于可分辨尺度。

## 1. 判定依据

### 1.1 标准指标（AP50，见 [指标协议](competition_detection_metric_protocol.md)）

| 画布 | traffic light AP50 | 全类 mAP50 | 红绿灯 AP50 相对全类 |
| --- | ---: | ---: | ---: |
| 320×192 | 0.0156 | 0.1122 | 0.14× |
| 416×256 | 0.0432 | 0.1675 | 0.26× |
| 512×288 | 0.0712 | 0.1999 | 0.36× |
| 640×352 | 0.1039 | 0.2329 | 0.45× |
| 640×384（对照） | 0.1055 | 0.2506 | 0.42× |

红绿灯始终是全类里最差的一类，即使把画布提到 640×384 也只有 AP50 = 0.106。

### 1.2 阈值能否救？——不能

同一份预测 dump 在多个阈值上重新计分（不重跑模型）：

| 画布 | conf | traffic light recall |
| --- | ---: | ---: |
| 512×288 | 0.25 | 0.0516 |
| 512×288 | 0.10 | 0.1006 |
| 512×288 | 0.05 | 0.1320 |
| 640×352 | 0.25 | 0.0797 |
| 640×352 | **0.10** | **0.1405** |
| 640×352 | **0.05** | **0.1876** |

即使把置信度压到 0.05（这个阈值在部署上会带来大量虚检），recall 也只有 0.188。而 640×360 + conf 0.05~0.10 正是本轮要求验证的组合——**明显不足**。

### 1.3 低 recall 的归因：不是"被阈值滤掉"

对每个 GT 框找同类、IoU ≥ 0.5 的最高分预测，区分"不可达"与"可达但低分"：

| 画布 | GT | 不可达（任何分数下都无候选） | 不可达比例 | 可达且 ≥0.25 | 可达但 <0.25 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 512×288 | 2734 | **2149** | **78.6%** | 141 | 444 |
| 640×352 | 2734 | **1949** | **71.3%** | 218 | 567 |

- 512×288 的 recall 硬天花板是 **0.214**；640×352 是 **0.287**。无论阈值怎么调都超不过去。
- 降到 0.05 最多额外救回 16.2%（512×288）/ 20.7%（640×352）的 GT。
- 所以主因是"**根本没有预测**"，次要因是"有低分预测"。

### 1.4 物理原因：目标尺寸

| 画布 | letterbox 缩放 | 红绿灯中位框（原图 13.0 × 20.0 px）在模型空间 |
| --- | ---: | --- |
| 320×192 | 0.2500 | 3.3 × 5.0 px |
| 416×256 | 0.3250 | 4.2 × 6.5 px |
| 512×288 | 0.4000 | 5.2 × 8.0 px |
| 640×352 | 0.4889 | 6.4 × 9.8 px |
| 640×384 | 0.5333 | 6.9 × 10.7 px |

GT 尺寸分布：中位 13.0 × 20.0 px，中位面积 260 px²，**86.9% 小于 32×32**，只有 3.1% 小于 8×8。

所以"是否仍有大量目标物理尺寸 < 8 px"的答案是：**在原图上不是（只有 3.1%），但在模型空间上是**——即使 640×384 也只有 6.9 × 10.7 px，而最小特征层是 stride 8。红绿灯正好卡在这个尺度以下，P3 特征图无法表达它。

## 2. 建议：FRONT-only 专用支路（本轮不执行训练）

以下只作为方案，不在本轮启动。

### 2.1 形态

在 FRONT 之后串一个专用小目标头，只处理红绿灯：

```
FRONT 帧 (1280x720)
  -> ROI 裁剪：上 45% 高度（640x158 -> 补齐到 640x160 的合法画布）
  -> 专用 detector（小目标、单类、可带颜色分类）
  -> 与主检测器的红绿灯框融合（IoU 去重，保留高分）
```

- **ROI 依据**：违规红绿灯在道路视角下位于画面上半部；裁剪后目标相对尺度提升约 2.2×，等效于把 13×20 px 的目标放大到 29×44 px。
- **为什么用独立头而不是提高主检测器分辨率**：主检测器的画布已经证明要 640×384 才能到 AP50 0.106，而完整 1280×720 画布在 RK3566 上不可行（像素是 640×352 的 4.5 倍，NPU 时间将超过 200 ms）。

### 2.2 目标帧率

3–5 FPS。红绿灯是低频事件，不需要与主检测器同帧率。

### 2.3 预计算力预算（基于本轮板端实测）

| 项目 | 数值 |
| --- | ---: |
| 主检测器 FRONT @ 640×352，板端 NPU p50 | 46.34 ms |
| 主检测器 FRONT @ 5 FPS 占用 | 232 ms/s ≈ 23% NPU 时间 |
| 专用头 ROI 画布 640×160（102k px，与 416×256 同量级） | ≈ 24 ms/次 |
| 专用头 @ 3 FPS | 72 ms/s ≈ 7% NPU 时间 |
| 专用头 @ 5 FPS | 120 ms/s ≈ 12% NPU 时间 |
| **合计（FRONT 512×288 @10 FPS + 专用头 @3–5 FPS）** | 约 42–47% 的 NPU 时间 |

结论：**算力上可行**，剩余余量足够另外三路 320×192 @6 FPS（3 × 6 × 16.12 ms = 290 ms/s ≈ 29%）。

### 2.4 需要的数据（当前没有）

| 需求 | 现状 |
| --- | --- |
| 小目标红绿灯框 | BDD100K 有框（本 holdout 2734 个），但**没有颜色状态** |
| 红黄绿状态标注 | 冻结 CSV 里没有；需要带 `trafficLightColor` 属性的完整标注或专门数据集 |
| 与部署相机几何一致的素材 | 只有用户手头的道路视频（无逐框标注） |
| 夜间样本 | 仓库里只有已标注渲染版夜间视频，**没有可用的原始夜间素材** |

### 2.5 必须设的验收门槛

任何专用头在合入前，必须同时满足：

1. 在冻结 BDD holdout 上红绿灯 recall ≥ 0.60（当前主检测器 640×352 的天花板是 0.287）；
2. 不改变主检测器在其余 6 类上的输出（同一 holdout 上逐类 recall 不退化超过 0.005）；
3. 板端实测满足 §2.3 的算力预算，且四路总请求帧率不掉。

## 3. 本轮不做什么

- 不训练任何红绿灯专用模型（本轮禁止 fine-tune）。
- 不修改竞赛最终配置的阈值——本轮只产出证据。
- 不把"降阈值"当成解决方案：它最多多救 16–21% 的 GT，同时会显著抬高虚检（640×352 下 0.05 阈值的虚检增长见 [指标对比](competition_metric_comparison.md) §4）。

## 4. ROI 放大可行性实测（2026-09-18 追加）：FAIL

> 问题：不训练，仅把前向 ROI 裁剪放大，能否让 traffic light 达到可用水平？
> **答案：不能。** Gate 判定 **TRAFFIC_LIGHT_SPECIALIST_REQUIRED** 维持不变。

协议：冻结 holdout 全部 1000 张、2734 个红绿灯 GT；ROI 裁剪后 letterbox 到目标画布，
原始 COCO-80 `yolo11n.pt`，检测框映射回全帧坐标；AP50 用 pycocotools（仅红绿灯类），
recall/precision 用全项目统一的贪心一对一 IoU0.5 口径。工具 `tools/traffic_light_roi_eval.py`。

ROI 定义：A=全帧；B=顶部 60%；C=顶部 50%；D=由 GT 统计自动确定（覆盖约 95% 红绿灯框的最小前向区域，
实测覆盖 94.4%——红绿灯在 y∈[0,58.5%]、横向几乎全宽，所以 D≈"全宽×顶部60%"）。

| ROI（面积） | 画布 | GT 覆盖 | 候选覆盖率 | AP50 | R@0.05 | P@0.10 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| A 全帧 (100%) | 512×288 | 1.000 | 0.221 | 0.0539 | 0.095 | 0.252 |
| D gt95 (57%) | 512×288 | 0.944 | 0.220 | 0.0545 | 0.090 | 0.245 |
| A 全帧 (100%) | 640×352 | 1.000 | 0.302 | 0.0806 | 0.141 | 0.267 |
| **D gt95 (57%)** | **640×352** | **0.944** | **0.323** | **0.0830** | **0.149** | **0.272** |

（B/C 介于两者之间且更差；完整 8 组合见
`D:/Datasets/adas_edge_training/roi_eval/TL-ROI-full.json`。conf sweep 0.05→0.25 单调下降，
0.05 已是最佳点。）

### 4.1 为什么 ROI 救不动

1. **放大量不够**：95% 分位 ROI 面积只有全帧的 57%，线性放大仅 ~1.32×。
   红绿灯中位 13×20 px 在 512×288 模型空间约 5.2×8.0 px，放大后 6.9×10.6 px——仍在
   stride-8 P3 特征的有效表达下限之下。
2. **候选框照样出不来**：最佳组合下仍有 **67.7% 的 GT 框完全没有候选**（1851/2734）。
   这与 §1.3 的归因一致：瓶颈是"网络不产生候选"，不是阈值过滤。
3. **相对全帧的增益只有 +0.008 recall / +0.002 AP50**——不显著，不值一条支路的算力。

### 4.2 假如 ROI 有效，NPU 预算够不够（仍记录，供专项模型设计参考）

四路 WRR-FAIR 满额运行时推理线程占用约 78%（FRONT 10×37.9ms + 三路 18×22.2ms）。
追加支路（按画布 NPU-only 实测）：

| 支路 | 3 FPS | 5 FPS |
| --- | ---: | ---: |
| ROI→512×288（30.42 ms） | +9.1% → 87% | +15.2% → 93% |
| ROI→640×352（47.66 ms） | +14.3% → 92% | +23.8% → **102% 不可行** |

即 512×288@3FPS 勉强放得下但几乎没有余量；640×352@5FPS 放不下。
专项模型应做成更小的画布（例如 ROI 裁剪上 ~256×160 级别），这只能靠训练一个专用小模型实现。

### 4.3 正式结论

**TRAFFIC_LIGHT_SPECIALIST_REQUIRED**——ROI 重采样属于"无训练手段的天花板"，已被实测封死。
下一步（下轮）应训练 front-only 专项小模型（方案见 §2），本轮不启动。
