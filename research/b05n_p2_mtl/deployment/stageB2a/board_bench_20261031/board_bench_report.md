# B-2a MTL INT8 RK3566 实机测速报告（60 帧本地回放）

日期：2026-10-31
板端：LubanCat RK3566 / RKNN Lite2 2.3.2 / 4×Cortex-A55
对照模型：B05N P2 十类 Raw-head INT8（现有正式 B 模型）
新模型：B05N P2 MTL B-2a INT8（15 输出）

## 0. 输入说明

板端没有找到单独命名为“60 帧”的文件。最接近且此前验证过的本地输入是：

`/home/cat/b05g_113421_3s.rgb` — 1280×720 RGB565LE，**90 帧**（3 秒 @30fps）。

本次取**前 60 帧**，两个模型使用完全相同的帧、相同的 letterbox 预处理（512×288、RGB）、相同阈值（conf 0.25 / NMS IoU 0.45）。因此结论适用于这两个模型的相对比较，不代表其它 60 帧子集。

测试期间：

- 已记录并临时停止 `adas-ai-bridge-live.service`，测试后已恢复原 B05N 配置并确认 active。
- Qt、`hud_bridge.py` 仍在运行（未修改），所以绝对 FPS 是“带 HMI 负载”的值。
- 未修改正式模型、Qt、FPGA/PCIe、内核或自启动配置。

- 完整单帧 p50：**3.55×**（+254.7%）

## 3. 输出语义检查（60 帧）

### 检测

| 指标 | B05N INT8 | B-2a INT8 | B-2a FP16 |
|---|---|---|---|
| 含交通灯的帧 | 57 / 60 | 44 / 60 | 47 / 60 |
| 交通灯框数 | 122 | 63 | 70 |
| 交通灯最高分 | 0.512 | 0.435 | — |
| 交通灯平均分 | 0.353 | 0.335 | — |
| car 框数 | 372 | 366 | 364 |
| person 框数 | 94 | 96 | 104 |

B-2a 的 car/person 与 B05N 接近，但**交通灯在 B-2a 上明显减少**：含灯帧 57→44，框数 122→63。B-2a FP16 也是 47/60、70 框，说明这不只是 INT8 量化，B-2a 模型本身在该场景的小交通灯召回就低于 B05N；INT8 再损失一点。

### 分割

B-2a INT8，60 帧全部非空：

- 车道前景占画面 2.81%（2.12%–3.76%）
- 斑马线占 1.81%
- 车道像素内：实线 26.0%（16.5%–41.1%），虚线 74.0%（59.0%–83.5%）
- 可行驶区域：direct 3.19%，alternative 1.40%

没有全零、全背景或类别塌缩；实线/虚线有合理区分，但实线占比偏低、可行驶区域面积偏小，和 B-2a 在 PC 上的表现一致。

## 4. 瓶颈

B-2a 单帧 p50 232.3 ms 中：

- RKNN 调用 161.2 ms（69%）
- 分割后处理 49.0 ms（21%）
- 检测后处理 10.4 ms
- 预处理 8.3 ms

RKNN 调用从 46.0 ms 涨到 161.2 ms（+115 ms），是主要增量。NPU 采样只有 ~48% 均值、70% 峰值，并未打满，说明瓶颈更像是：

1. 15 个输出（其中 3 个 288×512 分割图）的 runtime 输出搬移/反量化；
2. RKNN Lite Python 侧取回 2.2M 个分割值；
3. 分割 argmax 在 Python/NumPy 中又占 49 ms；
4. Qt + HUD 已占约 80% CPU，进一步放大了抖动（p95 569 ms）。

FP16 RKNN 更慢（60 帧 p50 489 ms），不能作为速度回退方案。

## 5. 结论

- **能跑**：B-2a INT8 在 RK3566 上可正常加载、15 输出、无推理异常；分割非全零。
- **速度**：连续 3.41 FPS，比原 B05N 的 10.45 FPS 慢 **3.55×**，FPS 下降 **67.4%**；AI Bridge 回放只有 3.33 FPS，10 Hz 下大量丢帧。
- **精度风险**：交通灯召回明显低于原 B05N（含灯帧 57→44，框数 122→63），FP16 也只有 47/60，属于模型级退化，不是单纯量化问题。
- **不建议替换正式模型**。若继续，优先优化输出/后处理（int8 输出、C 侧解码、降低分割输出分辨率）并补交通灯召回；当前版本只适合研究验证。
